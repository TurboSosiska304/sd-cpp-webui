# SD.CPP WebUI

Лёгкая веб-оболочка над `stable-diffusion.cpp`, предназначенная прежде всего для локального запуска генерации изображений через `sd-cli`.

Проект создаётся как собственный WebUI, а не как попытка повторить AUTOMATIC1111, ComfyUI или Forge.

Главная идея:

    браузер
        ↓
    WebUI
        ↓
    FastAPI backend
        ↓
    stable-diffusion.cpp / sd-cli
        ↓
    CPU / Vulkan / другие backend'ы
        ↓
    изображение


======================================================================
1. ЦЕЛЬ ПРОЕКТА
======================================================================

Проект должен превратить неудобный CLI stable-diffusion.cpp в нормальный
локальный WebUI.

Сейчас генерация через CLI требует вручную указывать примерно такую
команду:

    sd-cli \
        --diffusion-model ~/AI/Z-Image/models/z-image-turbo-Q6_K.gguf \
        --vae ~/AI/Z-Image/models/ae.safetensors \
        --llm ~/AI/Z-Image/models/Qwen3-4B-Q4_K_M.gguf \
        --backend "diffusion=vulkan0,te=cpu,vae=cpu" \
        -p "..." \
        -W 512 \
        -H 512 \
        --steps 9 \
        -o output.png

Это неудобно по нескольким причинам:

1. Нужно помнить огромное количество аргументов.
2. Нужно вручную указывать пути к моделям.
3. Нужно помнить, какой backend к какому компоненту относится.
4. Логи stable-diffusion.cpp находятся в терминале.
5. Смена модели требует ручного изменения CLI.
6. Нет нормального интерфейса настроек.
7. Нет единой точки управления моделями.
8. Нет удобного просмотра результата.
9. В дальнейшем хочется использовать разные модели и разные
   конфигурации без ручного редактирования команд.

WebUI должен решить эти проблемы.


======================================================================
2. ОСНОВНОЙ ПРИНЦИП
======================================================================

WebUI НЕ является новым inference engine.

Он не должен самостоятельно реализовывать:

- diffusion;
- transformer inference;
- GGUF loader;
- VAE;
- CLIP;
- Vulkan;
- CUDA;
- CPU kernels;
- scheduler;
- sampler;
- memory management stable-diffusion.cpp.

За это отвечает stable-diffusion.cpp.

Наш проект является управляющей оболочкой.

То есть:

    WebUI
       ↓
    формирует параметры
       ↓
    запускает sd-cli
       ↓
    получает stdout/stderr
       ↓
    показывает состояние пользователю
       ↓
    показывает готовое изображение


Это важнейшее архитектурное правило.

Если какую-то функцию можно реализовать средствами stable-diffusion.cpp,
предпочтительно использовать существующую функциональность sd-cli,
а не дублировать её в Python.

======================================================================

Он умеет:

- запускать FastAPI;

- запускать sd-cli;

- возвращать PNG;
- показывать PNG в браузере;

Текущая схема:

    Browser
       ↓
    POST /api/generate
       ↓
    FastAPI
       ↓
    StableDiffusionCPP.generate()
       ↓

       ↓
    sd-cli
       ↓
    PNG
       ↓
    /outputs/<uuid>.png
       ↓
    Browser

6. КЛЮЧЕВАЯ ТЕРМИНОЛОГИЯ
======================================================================

Важно не путать следующие понятия.

sd-cli
    CLI-программа stable-diffusion.cpp.

stable-diffusion.cpp
    Сам inference engine.

Backend
    Вычислительный backend ggml.
    Например CPU или Vulkan.

Device
    Конкретное вычислительное устройство.

Например:

    Vulkan0
        AMD Radeon RX 570 Series

    CPU
        AMD Ryzen 5 5600


Diffusion model
    Основная diffusion/DiT модель.

Text encoder / LLM
    В случае Z-Image это Qwen-based text encoder.
    В CLI он передаётся через `--llm`.

VAE
    Variational Autoencoder.

CLIP
    Отдельный компонент, используемый некоторыми моделями.
    Не следует автоматически предполагать, что каждая модель использует
    CLIP. Z-Image в текущей конфигурации использует LLM text encoder.

GGUF
    Формат весов, который используется stable-diffusion.cpp для ряда
    моделей и компонентов.

Safetensors
    Формат весов, который также поддерживается stable-diffusion.cpp.

7. ТЕКУЩАЯ ТЕСТОВАЯ СИСТЕМА
======================================================================

Проект изначально разрабатывается и тестируется на Linux.

Текущая система:

    GPU:
        AMD Radeon RX 570 / Polaris 10

    GPU backend:
        Vulkan / RADV

    CPU:
        AMD Ryzen 5 5600

    Inference engine:
        stable-diffusion.cpp

    Main diffusion model:
        z-image-turbo-Q6_K.gguf

    Text encoder:
        Qwen3-4B-Q4_K_M.gguf

    VAE:
        ae.safetensors

    Current backend assignment:
        diffusion=vulkan0,te=cpu,vae=cpu


Важно:

RX 570 является старой картой и имеет ограниченные возможности Vulkan/GPU.

Поэтому проект не должен предполагать наличие:

- CUDA;
- NVIDIA;
- tensor cores;
- modern matrix cores;
- BF16;
- FP4;
- современных специализированных AI-инструкций.

WebUI должен относиться к GPU как к абстрактному backend/device,
а не зашивать логику именно под NVIDIA.

======================================================================
9. ПОЧЕМУ НЕ НУЖНО ЖЁСТКО ПРИВЯЗЫВАТЬ UI К Z-IMAGE
======================================================================

Несмотря на то, что первым тестовым сценарием является Z-Image,
архитектура должна позволять использовать другие модели.

Нельзя делать:

    if model == "z-image":
        ...

во всех частях проекта.

Вместо этого должна существовать абстракция модели:

    Model
        name
        type
        diffusion_model
        text_encoder
        vae
        optional components
        backend configuration


Например:

    Z-Image Turbo
        diffusion = z-image-turbo-Q6_K.gguf
        llm = Qwen3-4B-Q4_K_M.gguf
        vae = ae.safetensors


В будущем:

    Another Model
        diffusion = ...
        clip_l = ...
        clip_g = ...
        vae = ...


UI должен отображать только те параметры, которые поддерживаются
конкретной моделью.


======================================================================
10. МОДЕЛЬНЫЙ МЕНЕДЖЕР — БУДУЩАЯ ФУНКЦИЯ
======================================================================

Одна из главных целей проекта:

Пользователь не должен вручную переносить модели в:

    ~/AI/Z-Image/models

или любую другую конкретную директорию.

WebUI должен уметь находить модели.

В перспективе пользователь должен иметь возможность сказать:

    "использовать эту модель"

и указать:

    /home/nik/Downloads/model.gguf

или другой путь.

WebUI должен уметь работать с файлами, находящимися где угодно,
если у процесса есть доступ к ним.


В дальнейшем можно добавить:

    Model Manager

который умеет:

- сканировать директории;
- индексировать найденные модели;
- определять расширение;
- определять тип файла;
- показывать размер;
- показывать путь;
- проверять доступность;
- назначать файл компоненту;
- удалять модель из индекса;
- добавлять произвольные директории.


Важно:

НЕ перемещать файлы без явного указания пользователя.

Модель должна оставаться там, где пользователь её хранит.

WebUI должен хранить ссылку/путь на модель.


======================================================================
11. ПОДДЕРЖКА "ЛЮБЫХ" МОДЕЛЕЙ
======================================================================

Фраза "подтянуть что угодно и откуда угодно" НЕ означает, что backend
магически сможет запустить абсолютно любой файл.

Есть два разных понятия:

1. WebUI может обнаружить/хранить путь к файлу.
2. stable-diffusion.cpp умеет загрузить и запустить этот файл.

WebUI отвечает за первое.

stable-diffusion.cpp отвечает за второе.


Поэтому архитектура должна позволять:

    model path
        ↓
    model metadata
        ↓
    sd-cli arguments


Если конкретная модель требует:

    --diffusion-model
    --llm
    --vae

WebUI должен уметь это представить.

Если другая модель требует:

    --clip_l
    --clip_g
    --vae

это тоже должно быть возможно.


======================================================================
12. BACKEND CONFIGURATION
======================================================================

Текущий backend:

    diffusion=vulkan0,te=cpu,vae=cpu


ВАЖНО:

stable-diffusion.cpp использует собственные имена компонентов.

Нельзя самостоятельно придумывать имена backend-компонентов.

Например, в ходе разработки была ошибка с:

    clip=cpu

и:

    llm=cpu

потому что backend assignment должен соответствовать тому,
что конкретная версия stable-diffusion.cpp реально поддерживает.


Перед добавлением backend option необходимо проверить:

    sd-cli --help

и:

    sd-cli --list-devices


WebUI должен постепенно перейти от ручного ввода backend string
к структурированным настройкам.


Например:

    Diffusion backend:
        Vulkan0

    Text encoder backend:
        CPU

    VAE backend:
        CPU


А backend string должен строиться backend manager'ом.


======================================================================
13. НЕ ПЕРЕДАВАТЬ RAW COMMAND LINE ИЗ FRONTEND
======================================================================

Frontend НЕ должен отправлять:

    "--diffusion-model foo --vae bar ..."

Frontend должен отправлять JSON:

    {
        "model": "...",
        "prompt": "...",
        "width": 512,
        "height": 512,
        "steps": 9,
        "seed": -1
    }


Backend самостоятельно строит CLI.


Это важно для:

- безопасности;
- валидации;
- переносимости;
- читаемости;
- будущего изменения sd-cli;
- предотвращения command injection.


======================================================================
14. SUBPROCESS
======================================================================

Запуск sd-cli должен выполняться через subprocess.

Предпочтительный вариант:

    subprocess.Popen([...])

или:

    subprocess.run([...])

Команда должна передаваться как list[str].

НЕ использовать:

    shell=True


Нельзя собирать одну огромную shell-команду через строковую
конкатенацию.


Плохо:

    command = f"sd-cli -p '{prompt}' ..."

Хорошо:

    command = [
        sd_cli,
        "-p",
        prompt,
        ...
    ]


Это особенно важно для prompt, потому что prompt содержит:

- кавычки;
- скобки;
- запятые;
- спецсимволы;
- переносы строк;
- Unicode.

16. STREAMING LOGS
======================================================================

Целевая схема:

    sd-cli
       │
       │ stdout/stderr
       ▼
    subprocess.Popen
       │
       ▼
    Python async reader
       │
       ▼
    Job Manager
       │
       ▼
    WebSocket
       │
       ▼
    Browser


Frontend должен видеть логи в реальном времени.


Например:

    [INFO] loading model
    [INFO] loading tensors
    [INFO] graph cut
    [INFO] sampling
    [INFO] step 1/9
    [INFO] step 2/9
    ...
    [INFO] image saved


Не нужно пытаться парсить каждый лог сразу.

Сначала нужно просто показать raw log.

После этого можно добавить parser.


======================================================================
17. JOB MANAGER
======================================================================

Когда генерация становится асинхронной, каждая генерация должна иметь:

    job_id


Например:

    4fca2a2d5a9c...


Job:

    {
        "id": "...",
        "status": "running",
        "prompt": "...",
        "started_at": "...",
        "finished_at": null,
        "output": null,
        "error": null
    }


Статусы:

    queued
    running
    completed
    failed
    cancelled


В будущем это позволит:

- запускать генерацию;
- отслеживать прогресс;
- отменять генерацию;
- хранить историю;
- отображать несколько задач.

======================================================================
24. ERROR HANDLING
======================================================================

Ошибки sd-cli НЕ должны превращаться в:

    "Something went wrong."


Пользователь должен увидеть реальную причину.


Например:

    Vulkan device lost

    Not enough memory

    model file not found

    unsupported model

    invalid argument


Особенно важны ошибки VRAM.


Например:

    model manager cannot make enough memory available


Это означает проблему доступной памяти GPU,
а не проблему frontend.


Frontend должен показать:

    Generation failed

    <реальная ошибка>


и при необходимости дать пользователю открыть полный log.

25. VRAM
======================================================================

WebUI не должен самостоятельно решать VRAM management,
если stable-diffusion.cpp уже умеет это делать.


Например:

    --max-vram
    --auto-fit
    --offload-to-cpu
    --params-backend


должны использоваться через sd-cli,
если это необходимо.


WebUI может предоставить UI для этих настроек,
но не должен копировать реализацию model manager.


======================================================================
26. ПРОБЛЕМА 1024x1024
======================================================================

На текущей RX 570 генерация 512x512 работает.

При 1024x1024 stable-diffusion.cpp может выдать:

    reported free ~1.68 GB
    need ~3.04 GB


Это означает, что GPU не может выделить необходимую память
для соответствующего сегмента вычислений.


В таком случае WebUI должен:

1. не падать;
2. не зависать;
3. показать stderr;
4. сохранить job status = failed;
5. показать пользователю причину.


В дальнейшем можно добавить автоматические варианты:

    lower resolution
    VAE tiling
    CPU offload
    max VRAM
    auto-fit


Но только после базовой реализации.

30. SECURITY
======================================================================

Первоначально сервер должен слушать:

    127.0.0.1


Не:

    0.0.0.0


Пока не реализована аутентификация.


Причина:

WebUI запускает локальный процесс с правами пользователя.

Если открыть такой сервер наружу без защиты,
клиент сможет потенциально запускать произвольные операции,
связанные с inference.


Поэтому:

    localhost first.


Если в будущем понадобится доступ по LAN,
нужно отдельно реализовать:

- authentication;
- authorization;
- safe model paths;
- request limits;
- process limits.


======================================================================
31. PROMPT SECURITY
======================================================================

Prompt передаётся как отдельный аргумент subprocess.


Никогда не выполнять:

    eval(prompt)

или:

    os.system(prompt)


Prompt является обычными данными.


======================================================================
32. PATH SECURITY
======================================================================

Когда появится Model Manager,
пути к моделям должны валидироваться.


Нельзя позволять frontend передавать произвольные shell commands.


Разрешено:

    model_path = "/home/nik/models/foo.gguf"


Не разрешено:

    command = "rm -rf ..."


Frontend никогда не должен управлять shell.


======================================================================
33. ЛОГИРОВАНИЕ BACKEND
======================================================================

Python backend должен использовать стандартный:

    logging


а не:

    print()


Пример:

    logger.info("Starting generation")
    logger.error("Generation failed")


Для sd-cli stdout/stderr должны отдельно сохраняться
для текущего job.

48. PERFORMANCE
======================================================================

Основной bottleneck — inference.

FastAPI не должен создавать значительную нагрузку.


Не надо оптимизировать Python раньше времени.


Основные потенциальные проблемы:

- RAM;
- VRAM;
- Vulkan;
- disk I/O;
- model loading;
- VAE;
- diffusion compute.


WebUI должен быть максимально лёгким.


======================================================================
49. КОД
======================================================================

Основные правила:

- Python 3;
- type hints;
- небольшие функции;
- классы только там, где они действительно полезны;
- не дублировать код;
- не смешивать frontend и backend;
- не смешивать model management и generation;
- не использовать глобальные mutable state без необходимости;
- не использовать shell=True;
- не скрывать stderr;
- не проглатывать exceptions.


Код должен быть понятен человеку,
который откроет проект через несколько месяцев.

67. LOG STREAMING
======================================================================

При streaming необходимо аккуратно читать:

    stdout
    stderr


Не блокировать процесс ожиданием одного из потоков.


Иначе возможна ситуация,
когда buffer одного потока заполнится
и sd-cli зависнет.


Поэтому для production-версии нужно использовать
корректный asynchronous/subprocess pattern.

79. ПРИНЦИП "BACKEND FIRST"
======================================================================

    prompt
    settings


Backend решает:

    CLI arguments
    model paths
    backend assignment
    process


Это позволяет заменить frontend,
не переписывая inference layer.


======================================================================
80. ПРИНЦИП "MODEL PROFILE FIRST"
======================================================================

Когда появится несколько моделей,
нужно избегать огромного количества:

    if/elif


Вместо этого:

    model profile


Например:

    ModelProfile


который содержит информацию
о необходимых компонентах.


Это позволит добавить новую модель
без переписывания всего WebUI.
